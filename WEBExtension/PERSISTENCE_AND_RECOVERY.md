# Local persistence and continuation

Current frozen scientific study directories are listed in `artifacts/active_machine_runs.json`. Previously completed responses, question records, actor/critic parameters, optimizer state and Torch RNG records are retained. The earlier durability recovery changed no scientific settings. A subsequent user-authorized 100/30/300 revision is frozen as a new study; the original study, settings and artifacts remain preserved. See `artifacts/sample_size_revision_100_30_300/revision.json`.

The user authorized replacement attempts only for two interrupted requests after trying recovery. Azure's stored-completion list returned zero records and both original requests omitted `store=true`. Local response/temp searches also found no response. The authorization file binds the exact original attempt ID, key and request checksum. Original outcomes and costs remain unknown and potentially billed; they are never labeled as ungenerated or assigned zero usage. A replacement is a new, separately recorded attempt. Future ambiguous attempts still block until recovered or explicitly authorized.

`analysis/durable_worker.py` adds operational persistence around the existing code. Every JSON commit flushes the file and directory before returning. Transport bodies are saved before parsing and before the normal cache save. Dispatch receipts bind bodies to requests; complete staged responses can reconstruct the canonical cache after an interruption, avoiding regeneration. Authentication/request headers and API keys are excluded. Complete raw provider bodies, selected response IDs, refused outputs, usage, errors, parsed outputs and exact requests remain local.

Each worker session has `runtime_sessions/<session>/events.jsonl`, `timings.jsonl`, `parsed_call_outputs.jsonl`, its operational source snapshot, session start/end records, and PPO `optimizer_updates` archives. Every actual optimizer step saves model parameters, optimizer state and Torch RNG. Collection and validation checkpoint saves receive immutable content-addressed copies in `checkpoint_history`. Actual rollout tensors used by each PPO update are saved. Epoch-selected checkpoints and validation results remain under the original seed directories.

Timing records distinguish inclusive local backend/cache/queue time, network request/response time, stage time, PPO time, checkpoint I/O time, session wall time and local process CPU time. UTC timestamps are recorded. Server-internal compute time is not exposed and is not invented. Earlier unobserved timings cannot be reconstructed exactly; original call timestamps and latency fields remain available. Nested timing measurements overlap and must not be summed as independent durations.

`runtime_progress.json` is refreshed every 30 seconds with PID, session, phase, saved-record counts and reported token totals. Physical unknown usage, including the original interrupted requests, stays explicit. A saved heartbeat alone does not prove a live process; inspect its timestamp and the user service. Workers stop before issuing another request if disk free space is below 512 MiB. Graceful termination waits for the current request to finish before stopping further calls. Power loss or network interruption before a response reaches disk can still leave an unknown request; no storage system can reconstruct bytes that were never received.

The jobs run as independent user services, not chat-attached tool sessions. They survive closing this chat but cannot run while the machine is powered off. Standard output/error and service timing are saved under each study's `service_logs`. Failed workers do not restart blindly. Successful responses and dataset/tokenizer/checkpoint files remain available for an explicitly resumed run. The actual trained checkpoint and complete result reports are claimed only when their original completion gates pass.

## Adaptive pacing speedup

The user authorized shorter adaptive request pacing and concurrent independent pipelines. `analysis/adaptive_pacing.py` reserves request starts under a brief shared lock and releases that lock during network I/O. Separate process-wide file locks limit network occupancy to two slots. The controller and controlled pipeline each retain sequential calls and their original question/optimizer dependencies. Initial start spacing is 2 seconds; after 25 successful calls spacing decreases by 10 percent toward a 1-second floor. Explicit 429 responses double spacing up to 60 seconds and impose a shared provider-directed cooldown. Only the existing bounded 429 rejection retry is automatic; timeout and uncertain-response guards remain. No model, decoding, prompt, sample, reward, epoch, checkpoint-selection or statistical rule changes. Each resumed session saves actual operational sources and settings. Speed gains are measured from actual returned responses and timestamps rather than assumed.

The additional E1 timeout replacement was separately authorized after a local response check and a provider stored-completion lookup returned no recoverable response. Its original attempt and possible unknown cost remain recorded. The new authorization binds exactly that timeout and the previously authorized old interrupted E1 attempt; it does not authorize any future ambiguous attempt.

For local runs, keep the laptop powered on, connected to the internet, and awake. Closing the chat is safe. Suspend, shutdown, or a disconnected network interrupts execution. Keep the laptop plugged in and disable automatic sleep for the run; closing the lid can suspend it unless lid behavior is configured otherwise. This work does not modify power settings automatically.
